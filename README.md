# Letter generation POC

A reference proof of concept for admin-driven letter generation with a staged reveal: new letters are visible to staff only until a staff user enables the run for external users.

- `backend/`: case-service (Spring Boot, Maven). Includes a simulated letter-generator that runs in the dev profile only.
- `frontend/`: Angular + Angular Material.

## Running it

You need Java 25 and Node 24.15 or later. Maven is downloaded by the wrapper.

**1. Backend** (port 8080, dev profile: H2 in memory, seed data, simulated generator). From `backend/`:

```bash
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
```

On Windows `cmd`, use `mvnw.cmd`. The database is in memory, so restarting the backend resets the demo.

**2. Frontend** (port 4200). From `frontend/`:

```bash
npm install
```

```bash
npm start
```

Open http://localhost:4200. Every backend endpoint is under `/api`, and the dev-server proxy (`frontend/proxy.conf.json`) forwards `/api/*` to `http://localhost:8080`, so no CORS configuration is needed.

**API versioning.** Every endpoint is versioned with Spring Framework 7 API versioning (`@GetMapping(version = "1")` etc.), read from the `Api-Version` header (`spring.mvc.apiversion` in `application.yaml`). Version 1 is the default, so requests without the header work. An unsupported version returns `400`.

**Tests.** Backend (146 tests, about 30s), from `backend/`:

```bash
./mvnw test
```

Frontend (34 component tests), from `frontend/`:

```bash
npm test
```

**API docs (Swagger UI).** With the backend running in the dev profile, open http://localhost:8080/swagger-ui/index.html. The OpenAPI document itself is at http://localhost:8080/v3/api-docs.

- To try requests, click **Authorize** and enter a mock user, e.g. `admin` / `admin`. The document is public; the API calls still need credentials.
- The docs are generated by springdoc-openapi 3.1.1 (built against Spring Boot 4.1). They're switched on only in `application-dev.yaml`; in any other profile both paths return 404 (`OpenApiDisabledByDefaultTest`).

- JPA entities with Lombok `@Getter` / `@Setter` / `@NoArgsConstructor`

- a service that maps entities to `…Response` records in a private `mapToResponse`, so entities never leave it

### Frontend notes

- Standalone components, signals (`input()`, `output()`, `signal`, `computed`) and built-in control flow (`@if`, `@for`). Zoneless, which is the Angular 22 default. Reactive Forms for the generate form.
- Material components only. Colours come from an M3 theme generated with `ng generate @angular/material:theme-color` from the UX mockup's brand blue (#1F4E79, primary) and green (#2E7D3E, tertiary).
- Custom CSS is flex/grid layout plus Material token overrides (`mat.*-overrides`) that use theme colours:
  - the two visibility chips: Staff only is neutral with a lock icon; Staff + External is tertiary green with a check
  - the toolbar's brand colour
  - white cards
  - the green "complete" progress bar
- **Dates** are shown and typed as dd/mm/yyyy, as in the mockup. `NativeDateAdapter` parses typed text with `Date.parse`, which reads 01/10/2026 as 10 January, so a small `UkNativeDateAdapter` parses day-first (with tests). A real build might use a date-fns or Luxon adapter instead.
- **Statuses** are calculated by the backend and shown as Queued, In progress, Complete and Needs attention. Enable stays disabled until a run is Complete. Its hint reads "Available when generation completes" for a Queued or In progress run, and "Generation stalled; contact support" for one that needs attention.
- **Generate:** the card disables Generate until both fields are set, while the eligible count is 0, or while the type has any Queued, In progress or Needs attention run. Each of these shows a `mat-error`.
- **No idempotency key.** The confirmation dialog does the POST itself and disables its buttons while the request is in flight. On a network error or 5xx it stays open with Retry. If the first attempt did reach the server, the retry gets `409 RUN_IN_PROGRESS` rather than creating a second run. A 409 or 422 closes the dialog with a snackbar message.
- **Polling:** `GET /api/letter-runs` is polled every `RUNS_POLL_INTERVAL_MS` (15s, an injection token) while any loaded run is Queued, In progress or Needs attention. Polling stops when none are, and when the page is destroyed.
- **Roles in the UI** (the Generate card for ADMIN, Enable for STAFF, routes) are only presentation. The server checks every call.

## Data model

There are three new tables, all owned by case-service. The existing tables don't change: the queue table only gets inserts (using its existing columns), and case-documents is only read. No columns, indexes or views are added to either.

| Table | Columns | Notes |
|---|---|---|
| `letter_run` | `run_id` (PK, generated), `letter_type`, `claim_submitted_date`, `visibility`, `total_requested`, `requested_by`, `requested_at`, `completed_at`, `released_by`, `released_at` | One row per Generate click. `total_requested` is set once at Generate. `completed_at` is set the first time every item has a document. Release changes only `visibility`, `released_by` and `released_at` |
| `letter_run_item` | `run_id`, `app_id`, `letter_type`; PK `(run_id, app_id)`; index `(app_id, letter_type, run_id)` | One row per application in a run. `letter_type` is copied from the run, so the visibility check needs no join |
| `letter_type_lock` | `letter_type` (PK) | One row per letter type, locked with `SELECT … FOR UPDATE` during Generate and never updated. Add a row in the migration that introduces a new letter type |

**How they link:**
- run → items by `run_id`.
- item → queue: one queue row per item, key `app_id || '_' || letter_type`, built in the insert.
- item → documents: matched on `app_id` + `letter_type` = `document_type`.
- The queue and documents links are logical, not foreign keys.

**Deliberately not stored:**
- the generated count and the run status: both calculated on read
- per-item status: derivable from the documents table and the queue flag
- the queue key on the item: built in the queue insert
- an idempotency key: the type lock plus the pending check already prevent duplicates
- an audit table: who generated and who released are on the run

The POC edits the V1/V2 migrations in place, because its database is in memory and rebuilt on every start. A real deployment would add new migrations instead.

## API errors

Errors are RFC 9457 `ProblemDetail` responses (`application/problem+json`) with a stable `code` property.

| Status | `code` | When |
|---|---|---|
| 400 | `VALIDATION_FAILED` | A body field or `page`/`size` is invalid. `errors` lists them |
| 400 | `UNKNOWN_LETTER_TYPE` | `POST /api/letter-runs` with a type that has no lock row |
| 400 | `BAD_REQUEST` | Missing header, an unreadable body (such as a bad date format), a non-numeric ID, or an unsupported `Api-Version` |
| 404 | `NOT_FOUND` | Unknown run, letter type or document (`EntityNotFoundException`), or an external document that isn't visible to external users |
| 409 | `RUN_IN_PROGRESS` | The type has queue rows still flagged N, from any source (this is also what stops a double submit) |
| 409 | `NOT_COMPLETE` | Release of a run whose `completed_at` isn't set |
| 409 | `ALREADY_RELEASED` | Release of a run that is already STAFF_AND_EXTERNAL |
| 422 | `NO_ELIGIBLE_APPLICATIONS` | Nothing to generate; nothing is written |

Unlisted `/api` paths, such as the removed revoke endpoint, get 401 or 403 from `denyAll()`, not 404.

All of these come from `common/exception/GlobalExceptionHandler`. Not found uses `jakarta.persistence.EntityNotFoundException`, as in the reference project; business-rule failures use `BusinessRuleException`, which carries its status and code. Spring Security returns 401 and 403 itself, before a controller is reached, so those responses aren't ProblemDetails in the POC.

## Demo walkthrough

Start both apps (see above), with a fresh backend. Switch users with **POC only: act as**, under the header.

The simulated generator makes 5 letters every 10s, and the page polls every 15s while anything is generating.

**1. Generate as admin**
1. As `admin`, pick **Letter type F**: "No new applications are awaiting this letter type." appears and Generate stays disabled.
2. Pick **Letter type A** (18 new applications) and any claim submitted date, then click **Generate**.
3. The dialog shows the type, date, 18 applications and "Initial visibility: Staff only". Click **Generate**.
4. A snackbar confirms. The run appears as *0 / 18 letters · Queued · Staff only*, and moves to *In progress* once the first letters exist.
5. Letter type A now shows "A run for this letter type is still generating. Wait for it to complete."

**2. Watch progress.** Within about 45s the row climbs to *18 / 18 · Complete*, and polling stops. "Enable for external users" was disabled with "Available when generation completes" until then.

**3. Check the external view before release**
1. Switch to `external` and open APP-0003, then **Show documents**.
2. Only `DOC-EXISTING-6` (LETTER_I) is listed. It's an existing letter with no run, so it stays visible. The new LETTER_A letter is hidden.

**4. Release as staff**
1. Switch to `staff`. The Generate card is replaced by "Generating letters is restricted to the Admin role."
2. Click **Enable for external users** on the LETTER_A run and confirm.
3. The chip becomes *Staff + External*, with "Enabled <date> by staff".

**5. Check the external view again.** As `external`, APP-0003 now lists the LETTER_A letter as well.

**6. Delete and regenerate.** Deleting a letter is an existing feature, stubbed here as an endpoint. From a shell, find APP-0003's LETTER_A doc ID:

```bash
curl -s -u staff:staff http://localhost:8080/api/staff/applications/APP-0003/documents
```

Then delete it, replacing `<docId>` with that ID:

```bash
curl -s -u staff:staff -X DELETE http://localhost:8080/api/staff/documents/<docId>
```

Then:
1. As `admin`, Letter type A now shows 1 new application. Generate it.
2. When the run completes, `external` sees APP-0003's regenerated letter hidden again, until staff enable run 2.
3. Other applications' LETTER_A letters (for example APP-0004) stay visible throughout.

**7. The stuck run**
1. As `admin`, generate **Letter type E** (5 applications). APP-0043 is configured to always fail.
2. The run stops at *4 / 5*. Two minutes after it was requested (the dev profile's `letters.needs-attention-after`), it shows **Needs attention**, and Enable says "Generation stalled; contact support".
3. Within a minute after that, the backend log shows `WARN … ALERT letter run <id> needs attention …`, repeated on every check while the run stays stuck.
4. A new LETTER_E run is refused (`RUN_IN_PROGRESS`), and so is a release (`NOT_COMPLETE`).
5. `GET /api/letter-runs/<id>/pending` (as `admin` or `staff`) lists `APP-0043`, the application with no letter.

**8. Revoke** (no endpoint or UI): see "Revoking a mistaken release" below.

## Design notes

### Data access: Spring Data JPA, with two exceptions

Entities and `JpaRepository` interfaces are used throughout, matching the Places Been API.
- **Schema:** Flyway owns it, and Hibernate runs with `ddl-auto: validate`, so a mismatch between an entity and the migrations fails at startup. That's also what the reference project plans to move to.
- **Open-in-view** is off. Services are `@Transactional` (`jakarta.transaction.Transactional`, as in the reference), and list queries fetch the letter type with `@EntityGraph`, so there's no lazy loading outside a service and no N+1.
- **Native SQL where JPA can't express the rule:** the eligibility rule and the generate `INSERT … SELECT` are native `@Query` methods. The eligibility rule reads the shared queue, which has no entity.

**The exceptions:**
- `LetterRequestQueueRepository` uses JdbcTemplate. The shared queue table has no primary key and its key column isn't unique, so it can't be a JPA entity. It still joins the surrounding JPA transaction.
- The simulated generator uses JdbcTemplate. It isn't part of case-service, and it talks to the database the way the real generator does.

### Generate: one transaction

`LetterRunService.generateLetters` runs the steps in this order:
1. Lock the type's `letter_type_lock` row (`@Lock(PESSIMISTIC_WRITE)`, which Hibernate renders as `SELECT … FOR UPDATE`). No row means the type is unknown: 400 `UNKNOWN_LETTER_TYPE`.
2. Check for pending queue rows (409 `RUN_IN_PROGRESS`).
3. Save the run.
4. Insert the run items (`INSERT … SELECT`, using the same eligibility SQL as the count). Zero items means 422 and a rollback.
5. Set `total_requested`.
6. Insert the queue rows from the items, building the key in the insert.

There's no idempotency key. The lock plus the pending check make a double click or a retry return 409 instead of creating a second run, and the UI disables the confirm button while the request is in flight. `GenerateConcurrencyTest` fails if the `@Lock` is removed.

Things to check on the real database:
- **Locking syntax.** Hibernate's dialect handles it, including `WITH (UPDLOCK, ROWLOCK)` on SQL Server.
- **Isolation.** The flow assumes READ COMMITTED.
- **Identity columns.** The schema uses `GENERATED BY DEFAULT AS IDENTITY`.

### Simulated letter-generator (dev profile only)

The generator lives in the `simulatedgenerator` package and is **not part of case-service**. It uses no case-service classes and talks only to the database, as the real generator does.

Every `simulated-generator.interval` (10s), it reads up to `batch-size` (5) rows flagged N. For each row it inserts a case-documents row and sets the flag to Y with `WHERE queue_key = ? AND generated_flag = 'N'`.

Application IDs in `simulated-generator.failing-app-ids` (`APP-0043`) always fail and stay N.

Letter type codes contain `_`, so the app ID is taken by stripping the known `_<letterType>` suffix from the queue key, not by splitting at the first underscore. **Confirm how the real generator parses the key.**

Scheduled jobs are switched on by `SchedulingConfig` (`letters.scheduling.enabled`, default true). Tests turn them off and call the jobs directly.

### Status and progress: calculated, never stored

`LetterRunStatusService.calculate` works out each run's figures whenever it's read:
- **Generated:** the run's items that have a case-documents row with the same app ID and letter type. It's only counted while `completed_at` is null.
- **Completion:** when generated equals `total_requested`, `completed_at` is set with a guarded `UPDATE … WHERE completed_at IS NULL`, so concurrent readers can't overwrite it. From then on the run always shows total / total, even if a letter is later deleted for regeneration.
- **Status,** checked in this order:
  1. COMPLETE if `completed_at` is set.
  2. NEEDS_ATTENTION if `requested_at` is older than `letters.needs-attention-after` (4h; 2m in the dev profile).
  3. QUEUED if nothing is generated yet.
  4. Otherwise IN_PROGRESS.

The only write on a read is that one-time `completed_at`. Listing active runs costs one count query per run that isn't complete; completed runs cost nothing.

`GET /api/letter-runs/{id}/pending` (ADMIN, STAFF) lists the run's app IDs that have no document yet.

### Release

`POST /api/letter-runs/{id}/release` (STAFF) is one guarded statement:

```sql
UPDATE letter_run SET visibility = 'STAFF_AND_EXTERNAL', released_by = ?, released_at = ?
WHERE run_id = ? AND visibility = 'STAFF_ONLY' AND completed_at IS NOT NULL
```

If no row is updated, the run is reloaded to choose the error: `409 ALREADY_RELEASED` if it's released, otherwise `409 NOT_COMPLETE`. Of two concurrent releases, only one can match. Release needs `completed_at` to be set, and any read of the run (the page's polling, or the job) sets it as soon as the last letter exists.

`admin` can release because it also holds STAFF. A user with only ADMIN can't.

### Visibility policy (security-critical)

`DocumentVisibilityPolicy.VISIBLE_TO_EXTERNAL` is the single definition of what an external user sees. For a document's (app ID, document type), the latest `letter_run_item` (highest `run_id`) decides:
- **No item:** visible (letters that existed before this feature).
- **The item's run is STAFF_AND_EXTERNAL:** visible.
- **Otherwise:** hidden.

It's a JPQL condition used inside the external queries in `CaseDocumentRepository`, not a Java filter after the query, so paging and counts over external documents stay correct. `GET /api/external/documents/{docId}` returns 404 for a hidden document, exactly as for a missing one, so it doesn't reveal that the document exists.

Three tests guard it:
- `DocumentVisibilityTest` exercises the real external endpoints. If the condition always allows, 6 of its tests fail.
- `ExternalEndpointGuardTest` fails if anyone adds an `/api/external/**` endpoint without adding it to the covered list.
- `GET /api/staff/applications/{appId}/documents` returns everything, with a `visibleToExternal` flag on each document.

The POC does not check that an external user may access a given application. The real system already does this and must keep doing it.

### Completion job and alerting

`LetterRunCompletionJob.check()` runs every `letters.check-interval` (1m) over the runs that aren't complete:
- It sets `completed_at` where every letter now exists, so completion sticks even if nobody opens the page.
- It logs `WARN … ALERT letter run <id> needs attention …` for each run that needs attention, on every check while the run stays stuck. Point log alerting at that text and de-duplicate there, or replace it with a metric.

Statuses are calculated on read, so the job isn't needed for them to be correct.

A NEEDS_ATTENTION run can't be released, and it still blocks new runs of its type, because its queue rows are still N. Once the last letters arrive it becomes COMPLETE, whatever its age.

### Single-pod scheduling

In production `LetterRunCompletionJob.check()` must run on one pod only (it's marked in the code). Running it on two pods won't corrupt data, since `completed_at` is set with a guarded update, but each pod would log the alerts. **This choice is yours.** Options, with no versions picked:

| Option | How | Notes |
|---|---|---|
| ShedLock | Annotation on the job, with a lock table in the same DB (JDBC provider) | Smallest change, and fits "one DB". Adds one table and one library |
| Spring Integration `JdbcLockRegistry` | Obtain a named lock in `check()` | Also DB-backed. More code than an annotation |
| Leader election (e.g. Spring Cloud Kubernetes, or a K8s Lease) | Only the leader runs scheduled jobs | No DB table. Ties the app to the platform |
| Quartz, clustered JDBC job store | Quartz owns the schedule | Heavyweight for a single job |
| Hand-rolled DB lock | `SELECT … FOR UPDATE` on a job-lock row inside `check()`, like `letter_type_lock` | No library. Needs care with lock timeouts |
| Separate single-replica deployment or K8s CronJob | Job runs outside the web pods | Clean separation. Adds an operational component |

### Swapping in the real identity provider

Everything identity-specific is in `security/SecurityConfig`:

1. Replace `httpBasic` and the `InMemoryUserDetailsManager` bean with the real mechanism, for example `oauth2ResourceServer(jwt)` for bearer tokens.
2. Map the IdP's groups or claims to the roles `ADMIN`, `STAFF` and `EXTERNAL`, for example with a JWT authorities converter. The `authorizeHttpRequests` rules and `Roles` don't change.
3. `requested_by` and `released_by` come from `Principal.getName()`. Decide which claim that should be (a stable user ID rather than a display name) and configure it.
4. **CSRF:** it's disabled for the POC because the API is stateless HTTP Basic. Keep it disabled only if the real API stays stateless with bearer tokens. With cookie or session authentication, re-enable it and have the Angular app send the token.
5. Remove the frontend's POC user switcher and its Basic-auth interceptor.

### Revoking a mistaken release

There's no endpoint or UI for this on purpose. A mistaken release is rare, so it's a manual, change-controlled database procedure:

1. Confirm the run ID with the person who released it (`released_by`, `released_at` on the run).
2. Raise the change through the usual database change control.
3. Run, in one transaction:

   ```sql
   UPDATE letter_run
   SET    visibility = 'STAFF_ONLY', released_by = NULL, released_at = NULL
   WHERE  run_id = :runId AND visibility = 'STAFF_AND_EXTERNAL';
   ```

4. Check that exactly one row was updated. External users stop seeing the run's letters at once, and staff can release the run again later.

Record who released and who revoked in the change ticket, since the run no longer keeps the release fields and there's no audit table. Letters external users have already downloaded can't be recalled. `DocumentVisibilityTest` runs this exact statement to prove it hides the letters.

## Decisions log

| Decision | Reason | Rejected |
|---|---|---|
| Synchronous generate in one local transaction | Hundreds of rows per run; all tables in one DB; atomic | Async chunked job; one message per application |
| Run items recorded once, queue populated from them | Fixed, auditable membership; no drift between our record and the queue | A direct insert-select into the queue |
| Link via app ID + letter type | The queue has no row ID; no new columns allowed; key not unique | A run_id column on the queue; repurposing existing columns |
| Progress = run items with a live document | Correct because of the eligibility rule; shares the visibility link | A key-only join to the queue (ambiguous on regeneration) |
| Lean schema: three new tables; only facts that can't be calculated are stored | Fewer values to keep in step with tables we don't control | Stored generated count, stored status, per-item status, audit table |
| Store `total_requested` and `completed_at` on the run | Total is fixed at Generate; completed_at freezes a finished run's display | Recounting everything on every read |
| Status calculated: Queued, In progress, Complete, Needs attention | Always correct; no sync job needed for correctness | A stored status column |
| Per-type lock + pending check | Prevents duplicates without extra state | An idempotency key |
| Revoke as a manual procedure | Rare; no extra endpoint or UI | A revoke endpoint or button |
| Needs attention = not complete N hours after the request; release blocked | The generator retries forever; never expose unreviewed letters | Partial release; deleting shared queue rows; stored last-progress time |
| Release and completion as guarded UPDATEs | Concurrent requests can't both succeed or overwrite `completed_at`; no row locks needed | Read-check-set with a row lock; optimistic `@Version` |
| Visibility as a SQL condition inside the external queries | Paging and counts stay correct; hidden rows never leave the database | A Java filter after the query |
| WARN logged on every check while a run needs attention | No stored state to detect the transition; alerting de-duplicates | Storing an "alerted" flag |
